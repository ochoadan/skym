## Smallest operation and unresolved behavior

**Proposed action:** deliberately submit the adapter's command through the game's own chat input. **Proposed observable result:** a bounded adapter response appears through the native system-message path. This observes a real native UI submission; it does not verify mining, inventory changes, contract completion, or another physical gameplay action.

The selected source declarations are `cGcTextChatInput.ParseTextForCommands(this, fixed_string_pointer)` and `cGcTextChatManager.Say(this, fixed_string_pointer, system_message_bool)`. NMS.py represents the string as `cTkFixedString[0x3FF]` and both native return types as void. These are upstream declarations to verify, not independently proven ABIs for version `179666`.

The upstream chat manager rewrites commands in a parsing detour and recognizes a system help/error message. It does **not** demonstrate that an unknown `/community` command produces a nested `Say` call on the same thread in this build. The probe leaves the submitted command unchanged and attempts to correlate and replace only that native system response. This is an engineering hypothesis until directly observed. A failed correlation must not become an unrelated chat replacement or a success record.

Avoid retaining native object pointers between callbacks. Keep callback work bounded; no network wait belongs in a game hook. A later asynchronous service response will need a separately verified presentation/lifecycle mechanism. Other upstream hooks, such as `cGcPlayerNotifications.AddTimedMessage`, `cGcInteractionComponent.DoInteractionEvent`, and `cGcSimpleInteractionComponent.DoAction`, are candidate future surfaces rather than verified alternatives. The [singleton/state implementation](https://github.com/monkeyman192/NMS.py/blob/b41bf9e6fdff1c833b77d805bb0c8da555c4ced4/nmspy/_internal_mods/singletons.py) and [decorators](https://github.com/monkeyman192/NMS.py/blob/b41bf9e6fdff1c833b77d805bb0c8da555c4ced4/nmspy/decorators.py) expose main-loop/state callbacks, but the selected adapter does not load them or rely on their cached game objects.

## Runtime behaviors relevant to the guard

The following are verified from **pyMHF 0.2.4 source**, not inferred from its README:

- [Pattern lookup](https://github.com/monkeyman192/pyMHF/blob/0c8ebc1c29074c5bc35207e0aff36d4035e20bac/pymhf/core/memutils.py) selects the first match; even its multiple-result option falls back to the first value. It is not an ambiguous-signature rejection mechanism. The adapter needs an independent all-match check and explicit executable allowlist before hook registration. File hashes used by pyMHF for caching do not implement that allowlist.
- [Loader ordering](https://github.com/monkeyman192/pyMHF/blob/0c8ebc1c29074c5bc35207e0aff36d4035e20bac/pymhf/core/mod_loader.py) instantiates a mod before registering its hooks. Constructor validation can therefore reject registration, while an external preflight must reject unsuitable environments before injection itself.
- [Launcher](https://github.com/monkeyman192/pyMHF/blob/0c8ebc1c29074c5bc35207e0aff36d4035e20bac/pymhf/main.py) merges configurations from installed `pymhflib` entry points, including for a standalone file. [Injected startup](https://github.com/monkeyman192/pyMHF/blob/0c8ebc1c29074c5bc35207e0aff36d4035e20bac/pymhf/injected.py) runs installed `pymhf_rtfunc` entry points before loading the user mod. Isolating dependencies and excluding installed NMS.py avoids its internal hooks/global initialization.
- Injected startup honors `gui.shown=false`. If HTTP endpoints and the optional HTTP extra are used, its HTTP server binds `0.0.0.0:5000`; this task uses neither. The separate execution console still listens on `127.0.0.1:6770` and executes supplied Python without authentication. `interactive_console=false` suppresses the launcher's interactive prompt, not that listener. This is trusted local developer tooling, not an acceptable remotely exposed platform interface.
- Launcher shutdown can terminate the target process. Ctrl+C is not evidence of a clean native unload. Initial removal should use normal game exit and a subsequent launch without the adapter. Hot reload and safe detachment remain separate unverified capabilities.

## Injector source defect found during execution

Inspection of the exact installed Pymem 1.14.0 wheel's `pymem/process.py::inject_dll_from_path` shows that after remote `LoadLibraryW` it returns local `GetModuleHandleW(basename)`. The selected pyrun-injected wheel's `dllinject.py` uses that result as a target base when computing the `run_data` address. A local base does not establish a remote base. The lab wrapper enumerates the remote modules, matches the exact selected path, substitutes the actual target base and validates the export RVA plus its initial bytes before execution. This is a correction based on selected source inspection; it does not alone diagnose the initial native fault. The source artifacts are precisely identified by the release URLs and wheel hashes above.

The same pinned `dllinject.py::write_to_mem` computes a two-byte-character allocation/copy length even for byte buffers and packed structures. Its write can read beyond the Python source buffer. The launcher adapter supplies an owned, explicitly terminated byte buffer, allocates/copies its exact byte length, verifies the written count, and frees an allocation on failed write. Synthetic WinAPI tests cover these bounds; subsequent attachment evidence distinguishes this revised loader from the earlier run. Installed wheel files remain unchanged.
